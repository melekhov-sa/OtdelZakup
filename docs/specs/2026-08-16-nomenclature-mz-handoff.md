# Задание: колонка «Номенклатура МЗ», кандидаты подбора и перенос в заказ клиента

Документ для исполнителя, который будет вносить изменения. Исполнитель начинает с нуля —
здесь есть весь нужный контекст. Читать целиком до начала работы.

---

## 1. Что за система

Связка из двух частей.

**Python-сервис «OtdelZakup»** — FastAPI + SQLite, каталог ~220 тыс. позиций.
Репозиторий: `C:\Projects\OtdelZakup`. Принимает заявку клиента (текст, Excel, PDF),
распознаёт метизы (болты, гайки, шайбы), извлекает атрибуты и подбирает позицию
из внутреннего каталога. Прод: `Srv-sq-b1`, путь `Z:\ProjectZ`, служба NSSM `OtdelZakup`,
порт 8000.

**1С** — конфигурация на платформе 8.3.27.2170. Внешняя обработка
`ОбработкаЗаявкиМП.epf` (лежит в `C:\1C\` и копией в `C:\Projects\OtdelZakup\`)
вызывает сервис по HTTP и складывает результат в справочник заявок.

Пользователь обработки — **МЗ, менеджер по закупкам**. Она знает номенклатуру
идеально и является источником истины о том, что подобрано верно.

## 2. Что уже работает — не переделывать

Обработка зарегистрирована в БСП как дополнительная (`Вид = "ДополнительнаяОбработка"`,
команда `ОткрытиеФормы`), см. модуль объекта обработки. Вызывается из формы
справочника `ЗаявкиОтделаПродажПоЗакупкам`.

HTTP-слой вынесен в **общий модуль конфигурации `РазборЗаявокAPI`** (клиентский;
флаг «Сервер» не ставить — служба 1С блокирует исходящие HTTP-соединения).
Его методы, вызываемые из формы обработки:

- `ПроверитьСоединение()`
- `РазобратьТекст(ТекстЗаявки)`
- `РазобратьЗаявкуИзДвоичныхДанных(ДвоичныеДанные, ИмяФайла, Подсказка)`

Результат разбора складывается в табличную часть **`РазборЗаявкиОтИИ`** справочника
`ЗаявкиОтделаПродажПоЗакупкам`. Существующие реквизиты ТЧ:

```
НомерПозиции, Наименование, Количество, ЕдИзмерения,
ТипИзделия, ПодтипИзделия, Размер, Диаметр, Длина,
Стандарт, Прочность, Покрытие, Покраска, Материал,

КомментарийМЗ, Пользователь, ДатаРазбора,
ПризнакРазбора, ФайлЗаявки, ЭтоРазборТекста, ЭтоРазборФайла
```

Ключевые процедуры модуля формы обработки (`Forms\Форма\Ext\Form\Module.bsl`,
номера строк — по текущей выгрузке):

| Строка | Процедура | Что делает |
|---|---|---|
| 355 | `ЗаполнитьДанныеТЗ` | Запросом читает ТЧ в реквизит формы `РазобранныеПозиции` |
| 486 | `ОтчиститьДанныеВЗаявкеПоРазбору` | Удаляет строки разбора перед повторным разбором |

Комментарии МЗ уже работают: форма `КомментарийПоРазбору` пишет `КомментарийМЗ`
в строку разбора.

## 3. Задача

Сейчас система подбирает номенклатуру, и на этом всё заканчивается. Нужно:

1. Дать МЗ проставить **правильную** номенклатуру в отдельной колонке рядом с подбором системы.
2. Показать ей остальных кандидатов подбора, которые сервис уже присылает, а обработка выбрасывает.
3. Перенести подтверждённые позиции в **заказ клиента**.
4. Накопить данные, по которым потом можно разобрать, почему система ошибалась.

Пункт 4 отдельной разработки не требует — данные накопятся сами, если сделать 1–3.

**Признак «подтверждено» не заводить.** Всё выводится сравнением:
`НоменклатураМЗ` равна `НашаНоменклатура` — система права; отличается — ошиблась;
пустая — строку не смотрели.

## 4. Изменения в конфигурации 1С

### 4.1 Новые реквизиты в ТЧ `РазборЗаявкиОтИИ`

| Реквизит | Тип | Назначение |
|---|---|---|
| `НоменклатураМЗ` | СправочникСсылка.Номенклатура | Что МЗ считает правильным |
| `ПеренесеноВЗаказ` | Булево | Строка уже уехала в заказ |
| `ЗаказКлиента` | ДокументСсылка.ЗаказКлиента | В какой именно заказ |
| `ИДСтрокиРазбора` | Строка(36) | Устойчивый ключ строки, UUID |

### 4.2 Зачем `ИДСтрокиРазбора`

Сейчас строка разбора ищется по составному ключу
«ПризнакРазбора + ДатаРазбора + Наименование + НомерПозиции».
В форме `КомментарийПоРазбору` стоит проверка `Если МассивСтрокРазбора.Количество() = 1`,
и при двух одинаковых наименованиях в заявке комментарий **молча не сохраняется**.
Это существующий дефект. Мы вешаем на тот же ключ ещё и таблицу кандидатов,
поэтому ключ надо чинить, а не наследовать.

При записи каждой строки разбора присваивать
`Строка(Новый УникальныйИдентификатор())` в `ИДСтрокиРазбора` (в `ЗанестиДанныеВЗаявку`).
Кандидаты связывать по нему. Форму `КомментарийПоРазбору` перевести на поиск по нему же.

Для уже существующих строк ID пустой — это нормально, старые строки остаются
на старом поиске. Отдельную миграцию не делать.

### 4.3 Новая ТЧ `КандидатыПодбора` в том же справочнике

| Реквизит | Тип |
|---|---|
| `ИДСтрокиРазбора` | Строка(36) |
| `Ранг` | Число(1,0), значения 1–5 |
| `Номенклатура` | СправочникСсылка.Номенклатура |
| `УИД_1С` | Строка(36) |
| `НаименованиеКандидата` | Строка(500) |
| `Совпадение` | Число(5,1) |
| `ПутьДоПозиции` | Строка(500) |

`НаименованиеКандидата` хранить обязательно, отдельно от ссылки: если позиции
по `УИД_1С` в базе нет, МЗ должна хотя бы видеть, что предлагала система.

Чистить `КандидатыПодбора` вместе со строками разбора в
`ОтчиститьДанныеВЗаявкеПоРазбору`.

## 5. Изменения в общем модуле `РазборЗаявокAPI`

Сервис **уже** отдаёт кандидатов, менять Python не нужно. В ответе
`POST /api/v1/parse-request` у каждой строки есть:

```json
"match": {
  "uid_1c": "...", "name": "...", "score": 92.5, "match_mode": "авто",
  "candidates": [
    {"rank": 1, "uid_1c": "...", "name": "...", "score": 92.5, "folder_path": "Метизы/Болты"},
    {"rank": 2, "uid_1c": "...", "name": "...", "score": 81.0, "folder_path": "..."}
  ]
}
```

До пяти кандидатов, отсортированы по убыванию `score`.

В `РазборЗаявокAPI` сейчас разбирается только `match.name` / `match.uid_1c` /
`match.match_mode` / `match.score`, а `match.candidates` игнорируется.

Что сделать:

1. В структуру позиции (`СтруктураПозиции()`) добавить поле `Кандидаты` — массив структур
   `{Ранг, УИД_1С, Наименование, Совпадение, ПутьДоПозиции}`.
   Поле `Кандидаты` в структуре уже объявлено, но никогда не заполняется — заполнить.
2. При разборе JSON пройти `match.candidates` и сложить в этот массив.
3. Ничего больше в модуле не трогать.

> Живую версию этого модуля я не видел — он в конфигурации, а не в `.epf`.
> Копия в `C:\Projects\OtdelZakup\1c\CommonModule_РазборЗаявокAPI.bsl` **устарела**
> (в ней нет `РазобратьЗаявкуИзДвоичныхДанных`, который есть в живой).
> Читать надо конфигурацию, репозиторную копию использовать только как ориентир.

## 6. Изменения в обработке `ОбработкаЗаявкиМП`

### 6.1 Запись кандидатов

В `ЗанестиДанныеВЗаявку` (строка ~509), в цикле по позициям:
сгенерировать `ИДСтрокиРазбора`, записать его в строку разбора, затем для каждого
кандидата из `Поз.Кандидаты` добавить строку в `КандидатыПодбора` с тем же ID.
`Номенклатура` заполнять по `УИД_1С` тем же способом, что и `НашаНоменклатура`
(`Справочники.Номенклатура.ПолучитьСсылку(Новый УникальныйИдентификатор(...))`).

### 6.2 Таблица разобранных позиций

В `ЗаполнитьДанныеТЗ` (строка ~355) добавить в запрос новые реквизиты.
В таблицу формы добавить:

- **Колонка `НоменклатураМЗ`** — редактируемая, обычный выбор из справочника номенклатуры.
- **Гиперссылка «Верно»** в каждой строке — клик копирует `НашаНоменклатура`
  в `НоменклатураМЗ` и сразу пишет в справочник. Если `НашаНоменклатура` пустая —
  гиперссылка недоступна.
- **Кнопка «Кандидаты»** в строке — открывает список пяти вариантов
  (наименование, процент совпадения, путь в каталоге). Выбор варианта заполняет
  `НоменклатураМЗ`. Если кандидатов нет — кнопка недоступна.

Условное оформление:

- `НоменклатураМЗ` заполнена и **не равна** `НашаНоменклатура` — выделить строку
  (это ошибка подбора, самое ценное для последующего анализа);
- `ПеренесеноВЗаказ = Истина` — приглушить строку, снять отметку по умолчанию.

Запись `НоменклатураМЗ` в справочник делать сразу по изменению ячейки,
не копить до закрытия формы: МЗ работает подолгу, потеря правок недопустима.

### 6.3 Перенос в заказ

Кнопка «Перенести в заказ» на форме. Активна, только когда обработка открыта
из заказа клиента.

Переносятся строки, у которых:

- заполнена `НоменклатураМЗ` (без неё строка в заказ не уезжает — это правило,
  заставляющее МЗ либо подтвердить подбор, либо выбрать позицию руками);
- `ПеренесеноВЗаказ = Ложь`;
- строка отмечена пользователем.

По нажатию форма собирает массив структур `{Номенклатура, Количество}`
и отдаёт его форме заказа (механизм — раздел 7). После успешного добавления
проставить в строках `ПеренесеноВЗаказ = Истина` и `ЗаказКлиента = <ссылка>`.

Единицу измерения **не переносить** — она подставится из номенклатуры штатным
механизмом заказа. Пустое количество перенос не блокирует: уходит ноль,
МЗ дозаполняет в заказе перед проведением.

## 7. Вызов из заказа клиента и возврат строк

### 7.1 Как открывается

Обработку нужно сделать вызываемой и из формы документа `ЗаказКлиента`.
При открытии из заказа обработке передаются параметры: ссылка на заказ.
Заявку обработка находит **по регистру сведений «Заказы по заявкам ОП»**
(точное имя регистра уточнить в конфигурации), затем заполняет таблицу
разобранных позиций как обычно.

### 7.2 Как возвращаются строки — важно

Прямую запись в объект заказа из обработки **не делать**. Если заказ открыт
и в нём есть несохранённые правки, запись объекта их затрёт; с новым, ещё
не записанным заказом это не сработает вовсе.

Обработка зарегистрирована в БСП с командой `ОткрытиеФормы`, штатного
возврата результата у такой команды нет. Поэтому:

**Форма обработки** по кнопке «Перенести в заказ» вызывает

```1c
Оповестить("ДобавитьПозицииВЗаказКлиента", СтруктураДанных);
```

где `СтруктураДанных` содержит ссылку на заказ и массив позиций.

**Модуль формы `ЗаказКлиента`** обрабатывает это в `ОбработкаОповещения`:
проверяет, что `СтруктураДанных.Заказ` совпадает с текущим документом
(иначе оповещение адресовано другому открытому заказу — проверка обязательна),
и добавляет строки в свою табличную часть **на клиенте**, без записи документа.

Так это работает с незаписанным и с изменённым заказом, ничего не затирает,
и МЗ видит результат до записи и может откатить.

## 8. Python-сервис менять не нужно

Кандидаты уже отдаются (`app/api.py`, функция `_build_candidate_list`, до пяти штук).
Никаких изменений на стороне сервиса эта задача не требует.

Отдельно: в модуле `РазборЗаявокAPI` зашиты адрес `127.0.0.1:8000` и **таймаут 60 секунд**.
Таймаут в рамках этой задачи не трогать, но иметь в виду: на больших заявках
(порядка 170 строк) разбор может в него не уложиться, и 1С оборвёт соединение
раньше, чем сервис ответит. Это отдельная известная проблема.

## 9. Сборка и выгрузка обработки

Платформа: `C:\Program Files\1cv8\8.3.27.2170\bin\1cv8.exe`.
База: `C:\Users\Administrator\Documents\InfoBase`, пользователь `МелеховС`, без пароля.

Выгрузить обработку в XML:

```
1cv8.exe DESIGNER /F "C:\Users\Administrator\Documents\InfoBase" /N "МелеховС" /DisableStartupDialogs /DisableStartupMessages /DumpExternalDataProcessorOrReportToFiles "<каталог>" "<путь>\ОбработкаЗаявкиМП.epf" /Out "<лог>"
```

Собрать обратно:

```
1cv8.exe DESIGNER /F "C:\Users\Administrator\Documents\InfoBase" /N "МелеховС" /DisableStartupDialogs /DisableStartupMessages /LoadExternalDataProcessorOrReportFromFiles "<каталог>\ОбработкаЗаявкиМП.xml" "<путь>\ОбработкаЗаявкиМП.epf" /Out "<лог>"
```

Код возврата не показателен — **проверять лог**: при ошибке аутентификации
процесс всё равно завершается с кодом 0, а в логе будет
`The infobase user is not authenticated`.

Исходники обработки в XML держать в git рядом с кодом сервиса. Сейчас в репозитории
лежит только бинарный `.epf` и устаревшие `.bsl` от 2 мая — из-за этого три месяца
изменений не видны в истории. Повторять это не надо.

## 10. Критерии приёмки

1. МЗ открывает обработку из заявки, видит колонку «Номенклатура МЗ» рядом с подбором системы.
2. Клик по «Верно» заполняет колонку подбором системы и сохраняет в справочник немедленно.
3. Кнопка кандидатов показывает до пяти вариантов с процентом и путём; выбор заполняет колонку.
4. Строки, где выбор МЗ разошёлся с подбором системы, визуально выделены.
5. Обработка открывается из заказа клиента, находит заявку через регистр, показывает позиции.
6. «Перенести в заказ» добавляет отмеченные строки в табличную часть **открытого**, ещё
   не записанного заказа; несохранённые правки заказа не теряются.
7. Повторное открытие обработки не даёт перенести те же строки второй раз.
8. В заявке с двумя одинаковыми наименованиями комментарий МЗ сохраняется корректно
   (проверка исправления составного ключа).

## 11. Что не проверено и требует уточнения на месте

- Точное имя регистра сведений «Заказы по заявкам ОП».
- Точное имя документа заказа (предполагается `Документ.ЗаказКлиента`).
- Живая версия общего модуля `РазборЗаявокAPI` — читать из конфигурации,
  репозиторная копия устарела.
- В модуле объекта обработки идентификатор команды —
  `"РеестрСчетовПоставщиковВнешняяОбработка"`, похоже скопирован из другой обработки.
  На работу не влияет, но при добавлении команды для заказа клиента имя стоит задать осмысленное.
