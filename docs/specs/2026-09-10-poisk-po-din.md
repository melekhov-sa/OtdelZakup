# Поиск по DIN: подбор позиций из внутреннего каталога через DIN-аналог

Спецификация. Режим подбора, при котором позиции по не-DIN стандартам ищутся
в нашем каталоге через свой DIN-аналог, а позиции по DIN остаются на своём
стандарте.

---

## 1. Что есть сейчас

### Механизм аналогов

Соответствия стандартов лежат в `StandardEquivalent` (таблица
`standard_equivalents`, поля `src_canonical`, `dst_canonical`, `is_active`).
Связь **симметрична**: `_load_analogs_from_db()` в
`app/matching/standard_analogs.py` кладёт в словарь обе стороны пары.

На 2026-09-10 в базе разработки 11 активных пар, и **в каждой одна сторона —
DIN**: ГОСТ↔DIN и DIN↔ISO. Транзитивных цепочек нет; `get_standard_analogs()`
делает ровно один шаг (параметр `max_depth` объявлен, но в теле не используется).

### Три режима подбора

`MatchSettings` (`app/match_settings.py`) несёт два флага:

- `use_standard_analogs_in_main_match` — искать дополнительно по аналогам
- `analogs_only` — искать **только** по аналогам, прямой запрос пропустить

Из них складываются три режима, которые в UI называются «Без аналогов» /
«С аналогами» / «Только аналоги» и передаются как `analog_mode` со значениями
`off` / `with` / `only`.

Режим влияет на подбор в трёх местах:

1. **`_query_minhash()`** (`app/matcher.py:163`) — генерация запросов к MinHash.
   При `analogs_only` прямой запрос пропускается; при включённых аналогах
   к нему добавляются запросы с переписанным текстом (`build_analog_queries()`
   подставляет вместо «ГОСТ 7798-70» строку «DIN 931»).
2. **`_build_exact_candidates()`** (`app/matcher.py:359`) — кандидаты первой
   стадии (точное совпадение типа и размера). Здесь считается признак
   «стандарт совпал напрямую / через аналог / не совпал» и по режиму
   отбрасываются лишние кандидаты.
3. **`filter_candidates()` и `_std_group()`** (`app/matching/post_filter.py:61`) —
   пост-фильтр: строит группу приемлемых стандартов и в режиме `analogs_only`
   требует строгого совпадения.

### Где режим выбирается

- Визарды загрузки — поле формы `analog_mode` в `view_raw.html`,
  `pdf_wizard.html`, `google_ocr_wizard.html`, `google_ocr_list_wizard.html`,
  принимается в `POST /transform` (`app/main.py:893`), сохраняется в
  `meta.json` файла.
- Заказы — `client_lines.html`, `choose_catalog.html`, `app/order_routes.py`.
- API для 1С — булев `use_analogs` в `/api/v1/match-request`,
  `/api/v1/parse-request`, `/api/v1/parse-request-base64`. Режима «только
  аналоги» в API нет.

### Почему существующих режимов недостаточно

Аналоги симметричны, а нужно направленное преобразование «любой стандарт → DIN».
Режим «Только аналоги» для строки по DIN уведёт поиск на ГОСТ — ровно то, чего
быть не должно. Режим «С аналогами» ищет по обеим сторонам сразу и оставляет
ГОСТ-кандидатов выше DIN-кандидатов в выдаче.

## 2. Что должно стать

Четвёртый режим — **«Поиск по DIN»**, значение `din`. Взаимоисключающий с тремя
существующими.

Решение принимается **для каждой строки отдельно**, по её стандарту:

| Стандарт строки | По чему ищем |
|---|---|
| `DIN 933` | по `DIN 933` — поведение режима `off` |
| `ГОСТ 7798-70`, есть аналог `DIN 933` | **только** по `DIN 933`; ГОСТ в поиске не участвует |
| `ISO 4017`, есть аналог `DIN 933` | **только** по `DIN 933` |
| `ГОСТ 1234`, DIN-аналога в справочнике нет | по `ГОСТ 1234` — поведение режима `off` |
| Стандарта в строке нет | поведение режима `off` — тип, размер, текст |
| Аналогов несколько (`DIN 931` и `DIN 933`) | по всем найденным DIN сразу |

**ISO считается чужим стандартом** и ведётся к DIN наравне с ГОСТом. `ГОСТ Р ИСО
4014` нормализуется в `ISO-4014` (уже реализовано в `_PREFIX_MAP`) и дальше
идёт как ISO.

### Два следствия, подтверждённые заказчиком

1. **Если DIN-аналог есть, а в каталоге по нему ничего нет — строка остаётся
   без подбора**, даже когда позиция по её родному ГОСТу в каталоге лежит.
   Отката на исходный стандарт в этом случае нет: откат работает только когда
   DIN-аналога нет в справочнике вовсе.
2. Молчаливый пропуск аналогов у стандартов без года чинится в рамках этой же
   задачи (раздел 5).

### Границы

- Режим влияет **только на подбор позиций из внутреннего каталога**.
- Выдача не меняется: в результате остаётся стандарт клиента, DIN нигде не
  подменяет исходные данные заявки, нормализованное наименование и правила
  готовности работают как прежде.
- В диагностике строки видно, по какому DIN шёл поиск (существующее поле
  `analog_info`, бейдж «через аналог» у кандидата).
- Охват: визарды загрузки файлов и API для 1С. Экраны заказов
  (`client_lines`, `choose_catalog`) и глобальная настройка `/settings/match`
  в этой задаче **не трогаются** — там остаются три прежних режима.

## 3. Контракт API

Во все три маршрута добавляется параметр `analog_mode` — строка со значениями
`off` / `with` / `only` / `din`.

- Параметр не передан → поведение как сегодня (глобальная настройка сервиса).
- Старый `use_analogs` продолжает работать: `true` → `with`, `false` → `off`.
- Пришли оба → главнее `analog_mode`.
- Неизвестное значение → трактуется как «не передан», ошибки нет.

`POST /api/v1/match-request` — JSON:

```json
{
  "rows": [
    {"row_no": 1, "code": "", "name": "Болт ГОСТ 7798-70 М12х60 кл.8.8", "qty": 100, "unit": "шт"}
  ],
  "analog_mode": "din"
}
```

`POST /api/v1/parse-request-base64` — JSON:

```json
{
  "file_base64": "UEsDBBQ...",
  "filename": "Заявка.xlsx",
  "analog_mode": "din"
}
```

`POST /api/v1/parse-request` — multipart/form-data: файл или текст плюс поле
`analog_mode` со значением `din`.

Структура ответа не меняется.

## 4. Изменения в коде

### 4.1 Разрешение режима для строки

Новая функция в `app/matching/standard_analogs.py`:

```
din_targets_for_row(row_dict) -> list[str]
```

Возвращает канонические DIN-ключи, по которым надо искать эту строку:

- стандарт строки не распознан → `[]`
- стандарт уже DIN → `[]`
- иначе → аналоги строки, отфильтрованные по префиксу `DIN-`

Пустой список означает «вести строку как в режиме `off`». Так оба случая
отката — нет стандарта и нет DIN-аналога — обрабатываются одинаково, без
отдельной ветки.

Стандарт строки берётся так же, как в существующем коде: сначала поля
`din` / `gost` / `iso` строки, затем — распознавание в тексте наименования.

### 4.2 Признак режима в настройках

В `MatchSettings` добавляется поле `din_only: bool = False`. Оно не попадает
в `_SETTING_KEYS` и не сохраняется в БД — это переопределение на один вызов,
как уже делается через `dataclasses.replace()`.

Комбинация `din_only=True` вместе с `use_standard_analogs_in_main_match` или
`analogs_only` не возникает: маршруты выставляют ровно один режим.

### 4.3 Генерация запросов — `_query_minhash()`

При `din_only`:

- считаем `targets = din_targets_for_row(row_dict)`
- `targets` пуст → прямой запрос, аналоговых запросов нет (как `off`)
- `targets` не пуст → прямой запрос **пропускается**, выполняются запросы
  с текстом, переписанным на каждый DIN из `targets`

`build_analog_queries()` получает необязательный параметр
`allowed_analogs: set[str] | None` — когда задан, переписывание идёт только
на эти ключи.

### 4.4 Кандидаты первой стадии — `_build_exact_candidates()`

Функция вычисляет целевые DIN сама, из `settings` и `row_dict`, которые ей уже
приходят. Параметром они не передаются: у функции четыре места вызова, и правка
каждого — лишний шанс пропустить одно и получить режим, который работает на
одном экране и молчит на другом.

- Целевые DIN не пусты: кандидат проходит, только если его `standard_key`
  совпадает с одним из них (сравнение через `same_standard()`, то есть без
  учёта года). Кандидаты без стандарта отбрасываются — иначе в режиме «только
  DIN» просочатся позиции с неизвестным стандартом.
- Целевые DIN пусты: ветка режима `off`.

Кандидат получает `match_standard_mode = "analog"` и `via_analog` с целевым
DIN — по ним UI рисует бейдж «через аналог», и видно, по какому DIN шёл поиск.

### 4.5 Пост-фильтр — `post_filter.py`

`post_filter_candidates()` вычисляет целевые DIN так же, из `settings` и
`row_dict`. Наружу параметр `din_targets` торчит только у
`compute_candidate_badges()` — её вызывают обе функции подбора.

Бейдж стандарта считается не через `_std_group()`, а прямым сравнением с
целевыми DIN (без учёта года). Позиция без стандарта получает `match=False`, а
не «нет вердикта»: в режиме DIN мы ищем один конкретный набор ключей, и всё
остальное — промах. Включается строгий режим, как у `analogs_only`.

### 4.7 Инвариант «DIN или ничего»

Этого в первоначальном разборе не было, а без него следствие 1 не выполняется.

В системе жёсткие фильтры **никогда** не приводили к «нет подбора». Когда
фильтр вырезал всех кандидатов, срабатывала лестница фолбэков
(`post_filter.py`, уровни 1-3) и возвращала их обратно, а итоговая позиция и
вовсе бралась из сырого MinHash в обход фильтра — `matcher.py`, комментарий
«Best item is still driven by raw MinHash Jaccard ranking». Признак
`best_filtered_out` блокировал только автоподстановку: строка всё равно
получала позицию в статусе «предложено».

В режиме `din` это ломало главное требование: строка по ГОСТу подбирала
ГОСТ-позицию, ровно ту, которую режим должен обходить.

Поэтому для режима `din` вводится отдельный инвариант:

- лестница фолбэков не спускается: если строгий фильтр вырезал всех, пост-фильтр
  возвращает пустой список и ставит в `filter_log` признак `din_no_match`;
- обе функции сборки результата (`decide_match()` и `add_internal_matches()`)
  при этом признаке возвращают режим `NONE` с причиной «Поиск по DIN: в каталоге
  нет позиции по DIN-аналогу».

На остальные три режима инвариант не распространяется — их поведение прежнее.

### 4.6 Точки входа

- `POST /transform` (`app/main.py:893`): `analog_mode` принимает значение
  `din`; ветка выставляет `din_only=True` и оба старых флага в `False`.
  Значение по-прежнему пишется в `meta.json`.
- Четыре шаблона визардов: новый пункт списка «Поиск по DIN» со значением `din`.
- `app/api.py`: `analog_mode` в `MatchRequestBody`, `ParseRequestBase64Body`
  и в форме `/parse-request`; `_apply_analog_override()` переписывается так,
  чтобы принимать и строку режима, и старый булев параметр.

## 5. Сопутствующая правка: аналоги для стандартов без года

`get_standard_analogs()` ищет точным совпадением ключа. Строка «ГОСТ 7798»
нормализуется в `GOST-7798`, а в справочнике лежит `GOST-7798-70` — аналог не
находится, и строка молча остаётся без DIN. При этом `same_standard()` год уже
отбрасывает, то есть в системе две несогласованные трактовки.

Правка: `_load_analogs_from_db()` дополнительно индексирует каждый ключ в форме
без года (`strip_edition_year()`), а `get_standard_analogs()` при промахе по
точному ключу пробует форму без года. Прежнее поведение при точном совпадении
сохраняется.

Правка затрагивает **все** режимы аналогов, не только новый: строки без года
начнут находить аналоги и в режимах `with` и `only`. Это исправление, но
поведение существующих режимов при этом меняется — учесть при проверке.

## 6. Риски

| Риск | Смягчение |
|---|---|
| Правки идут в `matcher.py` и `post_filter.py` — ядро подбора, где ломается то, что работает | Режим включается только явным `din`; при `din_only=False` все ветки исходные. Тесты на регресс трёх старых режимов |
| Строки без подбора из-за строгого «Только DIN» | Заказчик подтвердил осознанно. Диагностика показывает, по какому DIN шёл поиск |
| Справочник мал (11 пар) — режим повлияет только на болты, гайки, шайбы из этих пар | Проверить объём справочника на проде до внедрения; при необходимости пополнить |
| Правка года меняет поведение старых режимов | Отдельные тесты на `with` и `only` со стандартами без года |
| Кандидаты без стандарта отбрасываются в режиме DIN | Осознанное решение; проверить на реальной заявке, не рушит ли это подбор массовых позиций |

## 7. Тестирование

Модульные тесты `din_targets_for_row()`:

- `DIN 933` → `[]`
- `ГОСТ 7798-70` → `["DIN-933"]`
- `ГОСТ 7798` без года → `["DIN-933"]` (проверяет правку раздела 5)
- `ISO 4017` → `["DIN-933"]`
- `ГОСТ Р ИСО 4014` → `["DIN-931"]`
- `ГОСТ 9999` без соответствия → `[]`
- строка без стандарта → `[]`

Тесты подбора на тестовом каталоге:

- строка по ГОСТу, в каталоге есть позиция по DIN-аналогу → подбор находит её
- строка по ГОСТу, в каталоге только ГОСТ-позиция → подбора нет (следствие 1)
- строка по DIN → находит DIN-позицию, ГОСТ-позиция не подставляется
- строка без стандарта → подбор как в режиме `off`

Регресс: существующие тесты режимов `off` / `with` / `only` проходят без правок.

Проверка API: три маршрута с `analog_mode` равным `din`, со старым
`use_analogs`, и без параметров вовсе.

## 8. Что проверить до начала работы

1. Объём справочника соответствий на проде: сколько активных пар и во всех ли
   одна сторона DIN. Если появятся пары без DIN-стороны (ГОСТ↔ISO), потребуется
   обход в два шага — сейчас он не предусмотрен.
2. Есть ли в тестовом наборе заявка с ГОСТами, на которой виден эффект режима.
