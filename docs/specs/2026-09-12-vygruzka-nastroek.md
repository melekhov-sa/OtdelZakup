# Выгрузка и загрузка настроек

Снимок справочников, правил и настроек в файл — чтобы переносить их между
серверами и не терять при переустановке.

---

## 1. Зачем

Справочники и правила живут только в базе. Код их не содержит, git не хранит,
обновление не переносит. Обнаружилось это так: режим «Поиск по DIN» выкатили на
прод, а справочник соответствий стандартов там оказался пуст — пары заводили
только на машине разработки, и режиму нечем было работать.

Дальше будет хуже: закупщики ведут свои стандарты, правила и соответствия, и всё
это существует в одном экземпляре внутри `readiness.db`. Развернуть второй
контур или переустановить сервис — значит начать с нуля.

Нужен снимок: выгрузить файл на одном сервере, залить на другом.

## 2. Что делаем

Две кнопки на новой странице настроек:

- **Выгрузить** — скачивает JSON со всеми пользовательскими данными
- **Загрузить** — заливает такой файл, **полностью заменяя** содержимое этих
  таблиц

Слияния нет. Модель работы: один сервер — источник, где работают закупщики;
остальные — приёмники. Файл является снимком источника целиком.

## 3. Состав снимка

17 таблиц.

### Справочники

| Таблица | Что это |
|---|---|
| `standard_equivalents` | Соответствия стандартов (ГОСТ ↔ DIN ↔ ISO) |
| `standard_ref` | Справочник стандартов |
| `product_type` | Типы продукции |
| `system_tail_phrase` | Хвостовые фразы |

### Правила

| Таблица | Что это |
|---|---|
| `readiness_rule` | Правила готовности |
| `base_validation_rule` | Базовые правила проверки |
| `validation_rule` | Правила проверки |
| `validation_rule_exception` | Исключения из правил проверки |
| `coating_rule` | Правила покрытий |
| `strength_rule` | Правила класса прочности |
| `size_rule` | Правила размеров |
| `normalization_rules` | Правила нормализации |
| `inference_rule` | Правила логического вывода |

### Шаблоны и настройки

| Таблица | Что это |
|---|---|
| `name_template` | Шаблоны нормализованного наименования |
| `system_setting` | Настройки подбора, OCR и прочие системные |

### Группы объединения

| Таблица | Что это |
|---|---|
| `master_items` | Мастер-позиции |
| `master_item_members` | Состав групп |

Состав групп ссылается на каталог по GUID из 1С (`onec_guid`), а не по
локальному id, поэтому переезд переживает: после синхронизации каталога на новом
сервере связи останутся верными.

### Что в снимок не входит и почему

- **`internal_item`, `nomenclature_folder`** — каталог номенклатуры и папки.
  Приезжают из 1С через `app/sync_1c.py`. Восстанавливаются повторной
  синхронизацией, в файле были бы лишними сотнями мегабайт.
- **`supplier_internal_match`** — память подбора (мгновенное «Совпадение по
  памяти»). Ссылается на каталог по **локальному id**, который на другом сервере
  будет другим: перенос как есть указывал бы не на те позиции. Корректный
  перенос требует пересчёта через GUID — в первой версии не делаем, память
  накопится заново по мере работы.
- **Заказы, КП, сравнения, вложения, песочница, бенчмарки** — рабочие данные, а
  не настройки.
- **Кэш MinHash** — производная от каталога, строится сам.

## 4. Формат файла

Один JSON, UTF-8:

```json
{
  "format_version": 1,
  "exported_at": "2026-09-12T14:30:00+03:00",
  "app_commit": "6572297",
  "source_host": "srv-sq-t1",
  "tables": {
    "standard_equivalents": [
      {"id": 1, "src_canonical": "GOST-7798-70", "dst_canonical": "DIN-933",
       "confidence": 100, "is_active": true}
    ],
    "readiness_rule": []
  }
}
```

Строки выгружаются **со своими id**: снимок заливается в очищенные таблицы, и
сохранённые id держат связи между таблицами (например, исключения правил
проверки ссылаются на базовые правила по id).

Шапка нужна на загрузке: `format_version` больше известной — отказываемся сразу
и говорим почему, вместо падения на середине заливки. Остальные поля шапки
показываем пользователю перед заливкой: откуда файл и когда снят.

Даты пишутся строкой ISO 8601, при загрузке разбираются обратно.

## 5. Выгрузка

**Из интерфейса.** Кнопка «Выгрузить настройки» на странице `/settings/backup`.
Скачивается файл с именем вида `otdelzakup-settings-2026-09-12-1430.json`.

**Из консоли.** `scripts/export_settings.py <путь>` — тот же файл, чтобы можно
было повесить на планировщик Windows и складывать снимки по расписанию.

Обе точки зовут одну функцию сборки снимка — расхождений между ними быть не
может.

## 6. Загрузка

Страница `/settings/backup`, выбор файла, кнопка «Загрузить». Порядок:

1. **Разбор и проверка шапки.** Неизвестная `format_version` или битый JSON —
   отказ с текстом ошибки, база не тронута.
2. **Автобэкап.** Текущее состояние сохраняется в
   `data/backups/settings-<дата-время>.json` — тем же кодом, что и выгрузка.
   Не удался бэкап — загрузка не начинается.
3. **Замена.** В одной транзакции: очистка 17 таблиц, заливка строк из файла.
   Ошибка на любом шаге — откат, база остаётся прежней.
4. **Сброс кэшей.** 13 кэшей в памяти держат правила, настройки и справочники.
   Без сброса файл зальётся, а сервис продолжит работать по-старому до истечения
   TTL. Сбрасываются все:

   `invalidate_standard_analogs_cache`, `invalidate_readiness_caches`,
   `invalidate_category_validator_cache`, `invalidate_inference_cache`,
   `invalidate_settings_cache`, `invalidate_product_types_cache`,
   `invalidate_tail_phrases_cache`, `invalidate_coating_cache`,
   `invalidate_strength_cache`, `invalidate_size_cache`,
   `invalidate_normalization_cache`, `invalidate_match_memory_cache`,
   `invalidate_master_guid_cache`.

5. **Отчёт.** Таблица «что было → что стало» по каждой из 17 таблиц и путь к
   автобэкапу.

Таблицы, отсутствующие в файле, **не трогаются**: старый снимок не должен
вычищать то, чего в нём ещё не было. Таблица, присутствующая с пустым списком,
очищается — это осознанное «здесь пусто».

## 7. Риски

| Риск | Смягчение |
|---|---|
| Полная замена стирает правки на сервере-приёмнике | Автобэкап перед каждой заливкой. В описанной модели работы (один источник) правок на приёмнике быть не должно |
| Залили файл не того контура | Перед заливкой показываем шапку: хост-источник и дата снимка |
| Кэши отдают старые данные после заливки | Явный сброс всех 13, шаг 4 |
| Файл со старой схемой БД после миграций | `format_version` растёт при несовместимых изменениях; несовместимый файл отвергается |
| Заливка оборвалась на середине | Одна транзакция, откат целиком |

## 8. Тестирование

- Круговой прогон: выгрузить → изменить данные → загрузить → данные совпадают с
  выгруженными
- Загрузка на пустую базу наполняет все 17 таблиц
- Файл с `format_version: 999` отвергается, база не меняется
- Битый JSON отвергается, база не меняется
- Таблица отсутствует в файле — остаётся нетронутой
- Таблица присутствует пустым списком — очищается
- Автобэкап создаётся до заливки и читается обратно
- После загрузки кэш аналогов отдаёт новые данные, а не старые
- Каталог и заказы после загрузки не изменились
