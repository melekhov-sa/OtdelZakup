**Python-сервис «OtdelZakup»** — FastAPI + SQLite, `C:\Projects\OtdelZakup`.

## 2. Что уже есть — не переписывать

Механизм сравнения **полностью построен**, но доступен только через веб-интерфейс.
В JSON API для 1С его нет. Задача — обёртка, а не новый движок.

### Модели, `app/order_models.py`

```
Order          — заказ (контейнер сравнения)
ClientLine     — исходные строки клиента (в нашем сценарии не используются)
OrderItem      — позиция заказа: ссылка на каталог + нормализованные признаки
Supplier       — поставщик
Quote          — одно КП (файл от одного поставщика)
QuoteLine      — строка КП: raw_text, price, price_total, qty, unit,
                 нормализованные признаки, line_class, filter_reason
QuoteMatch     — привязка строки КП к позиции заказа
QuoteTable / QuoteOcrTable — сырые снимки таблиц из Excel и OCR
```

### Сервисный слой, `app/services/quote_order_matcher.py`

Чистые функции, от HTML не зависят — их и надо вызывать из API:

| Функция | Строка | Что делает |
|---|---|---|
| `match_quote_to_order_items(quote_id, session)` | 374 | Матчит строки одного КП к позициям заказа |
| `match_all_quotes_for_order(order_id, session)` | 473 | То же по всем КП заказа |
| `build_comparison_table(order_id, session)` | 504 | Собирает сводную таблицу |

`build_comparison_table` возвращает:

```python
{
  "suppliers": [имя, ...],
  "rows": [{"order_item": OrderItem,
            "cells": {имя_поставщика: {price, currency, unit, jaccard, mode, ql_id, quote_id}}}],
  "unmatched": {имя_поставщика: [QuoteLine, ...]},   # предложено, но не опознано
  "filtered":  {имя_поставщика: [QuoteLine, ...]},   # шапки, итоги, реквизиты, мусор
}
```

### Веб-маршруты как образец, `app/order_routes.py`

| Маршрут | Строка | Что переиспользовать |
|---|---|---|
| `POST /orders/{id}/approve` | 512 | Строки 537–555: построение `OrderItem` из `InternalItem` |
| `POST /orders/{id}/quotes/upload` | 608 | Разбор КП: Excel, CSV, текст, PDF/фото через OCR |
| `GET /orders/{id}/comparison` | 949 | Пример вызова сборки таблицы |

Матчинг идёт **не по строке**, а по нормализованным признакам: тип изделия,
размер, стандарт (с учётом аналогов ГОСТ/DIN/ISO), набор токенов и MinHash.
Поэтому «Болт М12х80 ГОСТ 7798 оц.» и «Болт оцинкованный 12*80 DIN 931» сходятся.
Разные наименования у поставщиков — это уже решённая задача, ничего делать не надо.

Неполное покрытие тоже решено: таблица строится по позициям заказа,
не предложил поставщик позицию — ячейка пустая.

## 3. Что делать

### 3.1 Миграция схемы (alembic)

Единица измерения и вес позиции приходят из 1С — у номенклатуры они заполнены.
Фасовку вытаскиваем из текста строки КП.

```
order_items:  + unit        String(50), nullable   — эталонная единица позиции
              + weight_kg   Float, nullable        — вес одной единицы, кг
              + qty         Float, nullable        — требуемое количество

quote_lines:  + pack_size   Float, nullable        — единиц в упаковке,
                                                     если распознано из текста

orders:       + external_ref String(100), nullable, index — идентификатор со стороны 1С
```

Приведённую цену **не хранить** — считать при сборке таблицы.

### 3.2 Три новых endpoint в `app/api.py`

Все под префиксом `/api/v1`, ответы JSON.

**Создать сравнение**

```
POST /api/v1/comparison
{
  "external_ref": "строка от 1С",
  "title": "Заявка №123",
  "positions": [
    {"uid_1c": "...", "qty": 100, "unit": "шт", "weight_kg": 0.085}
  ]
}
→ 200 {"comparison_id": 17, "positions_total": 30, "not_found": ["uid...", ...]}
```

Каждый `uid_1c` резолвится в `InternalItem` по полю `uid_1c`, из него строится
`OrderItem` — логика уже написана в `approve_catalog`, строки 537–555.
**Вынести её в отдельную функцию** и вызывать из обоих мест, не копировать.

`weight_kg` может не прийти или прийти нулём — это допустимо, см. раздел 4.
УИД, которых нет в каталоге, вернуть списком в `not_found`, позицию пропустить,
запрос не валить.

Если сравнение с таким `external_ref` уже есть — вернуть существующее и заменить
в нём позиции, а не плодить дубли.

**Загрузить КП**

```
POST /api/v1/comparison/{id}/quotes
{
  "supplier": "ООО Ромашка",
  "file_base64": "...",
  "filename": "price.xlsx",
  "hint": "table"
}
→ 200 {"quote_id": 42, "lines_total": 150, "matched": 28, "unmatched": 4, "filtered": 118}
```

**Обязательно JSON + Base64, не multipart.** 1С собирает multipart вручную строкой
и это ненадёжно — по этой причине для разбора заявок уже сделан
`/api/v1/parse-request-base64`, повторить тот же подход.

Поддержать те же форматы, что и веб: `.xlsx`, `.csv`, текст, PDF и изображения
через Google Document AI. Логика разбора есть в `quote_upload`, строка 608 —
вынести в сервис и вызывать из обоих мест.

После создания строк сразу вызвать `match_quote_to_order_items(quote_id, session)`.

**Забрать таблицу**

```
GET /api/v1/comparison/{id}
→ 200 {
  "comparison_id": 17,
  "suppliers": ["ООО Ромашка", "ООО Василёк"],
  "rows": [{
    "position_no": 1,
    "uid_1c": "...",
    "name": "Болт М12х80 ГОСТ 7798-70",
    "qty": 100, "unit": "шт",
    "cells": {
      "ООО Ромашка": {
        "price": 14.20, "currency": "RUB", "unit": "шт",
        "price_normalized": 14.20, "basis": "same_unit",
        "suspicious": false, "score": 92.5
      },
      "ООО Василёк": {
        "price": 167.00, "currency": "RUB", "unit": "кг",
        "price_normalized": 14.20, "basis": "weight",
        "suspicious": false, "score": 88.0
      }
    }
  }],
  "unmatched": {"ООО Ромашка": [{"row_no": 88, "raw_text": "...", "price": 12.0}]},
  "filtered_count": {"ООО Ромашка": 118}
}
```

`filtered` отдавать только счётчиком — это шапки и итоги, МЗ они не нужны.
`unmatched` отдавать списком: поставщик что-то предложил, а мы не опознали —
это МЗ видеть должна.

## 4. Пересчёт единиц измерения — правила

Самая ответственная часть. Поставщики дают цены в разных единицах, и наивное
сравнение чисел вводит в заблуждение сильнее, чем пустая ячейка.

**Железное правило: приведённая цена никогда не подменяет исходную.**
В ячейке всегда есть `price` и `unit` — факт из КП, как прислал поставщик.
`price_normalized` идёт рядом и всегда сопровождается полем `basis`.

Значения `basis`, в порядке убывания доверия:

| `basis` | Когда | Как считается |
|---|---|---|
| `same_unit` | Единица КП совпадает с единицей позиции | Без пересчёта |
| `pack` | В тексте строки КП распознана фасовка | `price / pack_size` |
| `weight` | Единица КП — кг, у позиции есть `weight_kg > 0` | `price * weight_kg` |
| `none` | Пересчёт невозможен | `price_normalized = null` |

Фасовке доверяем больше, чем весу: она из самого предложения поставщика,
а вес — из нашей карточки. Порядок проверки именно такой, как в таблице.

**Распознавание фасовки.** Поставщики пишут «уп. (100 шт)», «коробка 500 шт»
прямо в наименовании. Механизм разбора хвостов уже есть —
`app/parsing/tail_extractor.py` и `app/parsing/preprocess.py`, там же обрабатываются
«2,5 тыс. шт» и слитные формы «6шт». Переиспользовать, новый парсер не писать.

**Когда пересчёт невозможен** — `price_normalized = null`, `basis = "none"`.
Ноль, единицу или исходную цену не подставлять ни при каких обстоятельствах.
Пустое значение честнее неверного.

**Защита от кривого веса.** Вес в номенклатуре заполнен, но заказчик прямо
предупредил, что не идеален. Поэтому: если по позиции есть цены от двух и более
поставщиков и `price_normalized` расходится с медианой остальных более чем
в 10 раз — выставить `suspicious: true`. Ячейку **не прятать и не выбрасывать**,
пусть МЗ увидит и решит сама. Побочная польза — так найдутся ошибки в справочнике.

## 5. Что не делать

- **Не трогать веб-интерфейс.** Существующие маршруты `/orders/*` работают,
  ими пользуются. Общий код выносить в сервисы так, чтобы веб продолжал работать
  через них же.
- **Не менять формат `build_comparison_table`.** Пересчёт единиц делать слоем
  поверх, в API-обёртке, либо расширить функцию **добавлением** полей.
  Существующий шаблон `order_comparison.html` не должен сломаться.
- **Не делать выбор победителя.** Сервис отдаёт цифры, решение принимает МЗ.
- **Не трогать таймаут.** См. раздел 7.

## 6. Критерии приёмки

1. 1С создаёт сравнение, передав список УИД номенклатуры с количеством, единицей и весом;
   позиции, которых нет в каталоге, возвращаются списком, запрос не падает.
2. Загрузка КП работает для `.xlsx`, `.csv`, текста и PDF; файл передаётся Base64 в JSON.
3. После загрузки строки КП автоматически привязаны к позициям; в ответе счётчики.
4. Сводная таблица содержит строку на каждую позицию сравнения, включая те,
   которые не предложил никто.
5. Цена в килограммах при заполненном весе приводится к цене за штуку,
   `basis = "weight"`, исходная цена и единица сохранены в ячейке.
6. При пустом или нулевом весе `price_normalized = null`, `basis = "none"`.
7. Строка КП с фасовкой в тексте («уп. 100 шт») пересчитывается с `basis = "pack"`,
   и фасовка имеет приоритет над весом.
8. Расхождение приведённой цены с остальными поставщиками на порядок
   даёт `suspicious: true`, ячейка при этом остаётся в выдаче.
9. Строки КП, не привязанные ни к одной позиции, приходят в `unmatched`.
10. Веб-интерфейс `/orders/*` продолжает работать без изменений в поведении.

## 7. Известные ограничения и что не проверено

**Таймаут 60 секунд.** В общем модуле 1С `РазборЗаявокAPI` зашит таймаут HTTP-соединения
60 секунд и адрес `127.0.0.1:8000`. Разбор большого КП может в него не уложиться,
и 1С оборвёт соединение раньше, чем сервис ответит. В рамках этой задачи таймаут
не трогать, но при загрузке КП на сотни строк проблема проявится — заложить это
в тестирование и, если подтвердится, вынести отдельной задачей.

**Производительность.** По заказу с большим числом позиций и несколькими КП
матчинг ранее был узким местом; в мае проведена серия оптимизаций (кэш каталога,
индекс тип+размер по версии каталога, устранение линейного скана по 220 тыс. позиций).
Замерить время загрузки КП на 150+ строк и сравнить с таймаутом выше.

**OCR.** Путь PDF и фото идёт через Google Document AI и требует настроенных
параметров в `/settings/google-ocr`. Если не настроено — вернуть внятную ошибку,
а не исключение.

**Не проверялось при подготовке задания:** поведение `match_quote_to_order_items`
на `OrderItem`, созданных напрямую из каталога, минуя `ClientLine`. Логика построения
признаков та же, но проверить стоит в первую очередь — на этом держится весь сценарий.
